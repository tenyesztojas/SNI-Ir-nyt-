# ADR-010: RLS + server authorization defense-in-depth

**Status:** Accepted
**Date:** 2026-09-03

---

## Context

A Védett Karrier rendszer érzékeny felhasználói adatokat kezel (munkakörnyezeti preferenciák, kompatibilitási eredmények, Preferencialap). Egy egyrétegű védelmi megoldás (csak RLS, vagy csak server-side check) nem elegendő: RLS bug átengedi a kérést, de kliensoldali hiba is kijátszható.

## Decision

**Defense-in-depth: auth + server authorization guard + RLS minden érzékeny műveleten.**

Rétegek:
1. **Auth check** – `createClient()` session ellenőrzése minden Server Actionben
2. **Server authorization guard** – ownership check (pl. `career_profile.user_id === session.user.id`) minden mutáción
3. **RLS backstop** – Supabase RLS minden érintett táblán; ha a fenti két réteg hibázna, a DB elutasítja

Szabályok:
- RLS minden táblán aktív (`ENABLE ROW LEVEL SECURITY` + explicit policy minden táblán)
- Anon SELECT csak tervezett publikus adatokon
- `service_role` kizárólag `lib/supabase/admin.ts`-ben; normál flow-ban nem
- RLS nem kapcsolható ki workaroundként
- Érzékeny user log nem kerülhet kliensoldalra

## Alternatives Considered

- **RLS-only:** Elutasítva. A server side guard hiányában az ownership logika RLS-be kerülne, ami nehezebben auditálható.
- **Server-side only (RLS nélkül):** Elutasítva. Ha egy Server Action hibázik, nincs backstop.

## Consequences

- Minden új Server Action tartalmaz auth + ownership check-et.
- Minden új tábla tartalmaz RLS policyket (legalább: user saját adat, admin full access, anon limited).
- A `AUTHORIZATION_MATRIX.md` dokumentálja az összes érzékeny műveletet.
- Az RLS_MATRIX.md dokumentálja az összes tábla jogosultságait.

## Security/Privacy Implications

Ez az ADR az összes többi security döntés alapja. Megsértése kritikus incidens.

## Clean-Room Implications

A legacy táblák RLS-e érintetlen. Az új Védett Karrier táblák saját, auditált RLS policyket kapnak.
